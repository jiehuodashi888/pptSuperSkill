# 企业 PPT 多风格 SKILL 通用框架设计

## 1. 背景与决策

目标是把历史 PPT 的设计语言、模板和表达规范沉淀为可调用资产，并在生成新 PPT 时按业务场景自动选用正确的企业风格。系统服务多个相互独立的公司内网：通用能力持续演进，企业只维护自己的模板、规则、证据和映射关系。

已选择的实现路线是 **平台核心 + 企业实例包**：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 单一 SKILL + 每公司配置文件 | 不采用 | 配置、证据和模板容易串用，难以做版本及权限隔离。 |
| 平台核心 + 企业实例包 | 采用 | 通用能力可复用；企业数据、分类和模板可独立部署、审计和升级。 |
| 独立多租户服务平台 | 暂不作为 SKILL 首版范围 | 需要账号、服务、密钥和运行时治理，适合作为后续产品化层。 |

## 2. 目标、非目标与原则

### 目标

1. 学习同一公司、不同部门和场景的历史 PPT，形成多风格规范库。
2. 同时使用 PPTX 结构解析和页面渲染视觉分析；不能以单一视觉观察替代结构事实。
3. 将业务类型、视觉风格、页面结构三个维度独立管理，并允许风格标签组合。
4. 用证据、覆盖率、适用范围和置信度约束每一条规则。
5. 根据生成需求路由到企业实例内的风格、模板、设计 Token 和审核规则。
6. 对生成结果执行结构、视觉、内容和一致性审核，并可对安全的机械性问题自动修复。
7. 保留企业既有分类与资产；涉及破坏性分类变更必须人工批准。

### 非目标

- 不以通用分类覆盖企业既有部门、业务或风格体系。
- 不把企业 PPT 或抽取出的专有内容传入另一个企业实例。
- 不假设模型天然具备 PPTX 解析、渲染、并行调度或自动修复能力；这些能力必须由运行环境明确提供，并在不可用时安全降级。
- 首版不建设跨公司共享训练集、云端多租户服务、用户账号或权限系统。

### 设计原则

- **证据优先**：规则不是模型印象；必须可追溯到源文件、页码、元素或结构路径。
- **分层继承**：企业品牌基线、风格 Profile、页面模板和页面例外按优先级叠加。
- **分类保护**：未知归入候选/待确认，不自动创建、合并、删除或重命名正式分类。
- **契约优先**：Agent 间只能交换版本化 Schema 数据，不交换自由文本结论作为最终事实。
- **最小暴露**：核心读取企业包的受控接口，企业包只访问自己的根目录和运行数据。

## 3. 总体架构

```text
                     ┌─────────────────────────────────────┐
                     │          通用 PPT 平台核心           │
                     │ 调度 · Schema · 提取 · 聚类 · 生成 · QA │
                     └───────────────┬─────────────────────┘
                                     │ 受控实例接口
       ┌─────────────────────────────┼─────────────────────────────┐
       │                             │                             │
┌──────▼────────┐             ┌──────▼────────┐             ┌──────▼────────┐
│ 企业 A 实例包 │             │ 企业 B 实例包 │             │ 企业 N 实例包 │
│ 模板/风格/证据│             │ 模板/风格/证据│             │ 模板/风格/证据│
│ 分类/版本/策略│             │ 分类/版本/策略│             │ 分类/版本/策略│
└───────────────┘             └───────────────┘             └───────────────┘
```

核心不持久化企业原始 PPT，不内置企业名称、模板、品牌色或业务分类。它只定义工作流、Schema、验证器和包加载协议。企业实例包是唯一的企业事实来源。

### 3.1 生成引擎边界

首版以**从零生成可编辑 PPTX**为基线能力，不依赖企业模板；当企业后续提供 `.pptx`/`.potx` 模板时，使用同一生成契约增加“模板填充”适配器，而不改变路由、观察或审核数据结构。核心通过 `GenerationAdapter` 抽象三类模式：

| 模式 | 首版状态 | 用途 |
| --- | --- | --- |
| `native-create` | 必须实现 | 根据结构化页面计划、Token 和规则从零创建可编辑 PPTX。 |
| `template-fill` | 预留、可按实例启用 | 填充指定 PPTX/POTX 的已识别页面类型和占位符。 |
| `existing-deck-edit` | 预留 | 在批准的既有 PPT 上做局部更新。 |

生成器不绑定任何大模型。模型只负责按 Schema 输出页面计划、路由决策和审核解释；PPTX 写入、渲染和结构验证由本机可替换的工具适配器完成。任一模型替换不得改变实例包格式和核心 Schema。

### 3.2 能力探测与安全降级

每次运行先生成 `CapabilityManifest`。它记录本机及当前模型是否具备 PPTX 读取、PPTX 写入、渲染、图像理解、并行调度、浏览器访问和本地界面等能力；工作流据此选择路径，并在结果中写入实际覆盖率。

| 缺失能力 | 安全降级行为 | 禁止行为 |
| --- | --- | --- |
| 图像渲染或图像理解 | 只基于 PPTX 结构完成可验证观察；视觉氛围、裁切和重叠标为 `UNKNOWN` | 猜测视觉结论或宣称视觉 QA 已完成 |
| PPTX 结构读取 | 只对可读的 PDF/图片做视觉观察，并标记结构字段不可验证 | 伪造字体、母版、坐标或占位符事实 |
| PPTX 写入 | 输出页面计划、规则和人工操作清单 | 声称已交付可编辑 PPTX |
| 并行调度 | 九个观察员按相同任务契约串行执行 | 因串行而跳过观察员 |
| 本地界面 | 使用文件契约和命令入口完成审批与发布 | 阻塞学习、生成或审核主流程 |

九个观察员都必须实现完整的任务契约、输入校验、观察逻辑和结构化输出。降级仅降低某次运行可验证的观察范围；每个 Agent 都必须报告 `coverage`, `missing_capabilities` 和 `unknown_fields`。

## 4. 分层资产模型

每个实例的有效设计规范按以下顺序合并，后层只覆盖自己明确声明的字段：

1. `brand_baseline`：企业共享 Logo、品牌色、字体许可、页码和安全禁用项。
2. `style_profile`：如“经营分析”“技术方案”等已批准风格的设计和内容规则。
3. `layout_template`：封面、目录、KPI、对比、流程、图表、结论等页面结构契约。
4. `request_override`：本次生成明确指定且经校验允许的内容、比例或风格覆盖项。
5. `page_exception`：有证据、可追溯、仅对指定页面类型生效的例外。

不得用页面例外反向改写企业基线；不得把某一页的偶然设计升级为全局规则。

## 5. 多 Agent 职责与边界

### 协调与审核角色

| 角色 | 责任 | 不负责 |
| --- | --- | --- |
| `master-observer` | 编制任务、批处理、汇总、发现缺口与冲突 | 替代专家 Agent 下结论 |
| `final-auditor` | 验证证据、频率、适用范围和冲突；输出待确认项 | 擅自改变企业分类 |
| `scenario-style-router` | 将生成需求映射到已批准风格、模板和 Token | 创造未批准的风格或模板 |

### 九个专业观察员

| Agent | 主要产物 |
| --- | --- |
| `style-classifier` | 业务类型、视觉风格标签、相似度、候选分类、适用场景 |
| `typography-observer` | 字体、字号层级、字重、间距、对齐、数字与中英文规范 |
| `visual-style-observer` | 色彩 Token、渐变、形状、圆角、描边、阴影及使用语义 |
| `layout-observer` | 画布、栅格、边距、区域、对齐、密度和可复用布局模式 |
| `master-template-observer` | 母版、占位符、固定元素、模板类型、Logo、页眉页脚和页码 |
| `table-observer` | 表格类型、表头、边框、单元格、数字对齐、汇总和高亮规则 |
| `chart-observer` | 图表类型、坐标轴、图例、标签、数值格式、配色与禁用样式 |
| `visual-asset-observer` | 图片、图标、插画、裁切、清晰度、连线和装饰图形规则 |
| `content-observer` | 标题习惯、叙事结构、结论先行、信息密度、层级和总结模式 |

运行环境支持并行时，专业观察员可并行；否则同一份任务契约按阶段顺序执行，输出完全相同的结构化结果。

## 6. 三层观察流程

1. **Slide-level**：每页提取元素事实和视觉特征，所有发现指向页码/元素证据。
2. **Deck-level**：统计同一套 PPT 的重复模式，区分模板、通用规则和单页例外。
3. **Corpus-level**：在同一企业实例内跨文件聚类，分辨企业共用基线、部门差异和风格 Profile。

输入必须优先包含 `.pptx` 或 `.potx`；PPTX 结构可提供字体、坐标、主题和母版等可验证事实，渲染图像用于整体视觉、空间关系、裁切和视觉氛围判断。仅有 PDF/图片时，所有无法验证的结构字段必须标记 `UNKNOWN`。首版应支持每个实例 2–20 份历史样本；以单文件可恢复任务为最小调度单元，按容量串行或有限并行处理，而不是假设固定并发度。

## 7. 分类与路由

三类实体完全分离：

| 实体 | 回答的问题 | 示例 |
| --- | --- | --- |
| `business_type` | 这份 PPT 要完成什么业务目的？ | 年度经营汇报、技术方案、培训课件 |
| `visual_style` | 它采用何种视觉表达？ | 商务正式、数据驱动、科技感 |
| `layout_pattern` | 这一页如何组织？ | KPI、双栏、流程、对比、趋势图 |

一份 PPT 可有一个主要业务类型、一个主风格、多个辅助风格标签和多种页面结构。路由时应综合业务目的、部门/业务线（如已知）、受众、正式程度、交付媒介和显式风格选择；若匹配分数不达阈值，输出候选方案并请求确认，而非猜测。

## 8. 统一数据契约

核心 Schema 的首版必须至少定义下列对象：

| 对象 | 必填关键字段 |
| --- | --- |
| `SourceManifest` | `company_id`、`source_id`、`file_hash`、`ingested_at`、`access_scope` |
| `Evidence` | `source_id`、`slide_number`、`element_ref`、`source_type`、`locator` |
| `Observation` | `observation_id`、`category`、`fact`、`evidence[]`、`confidence`、`agent_id` |
| `Rule` | `rule_id`、`scope`、`statement`、`observed_value`、`priority`、`frequency`、`evidence[]`、`exceptions`、`status` |
| `StyleProfile` | `style_id`、`business_types`、`audience`、`tokens`、`rules`、`template_refs`、`version` |
| `RoutingDecision` | `request_facts`、`candidate_styles`、`selected_style_refs`、`template_refs`、`confidence`、`requires_confirmation` |
| `AuditFinding` | `finding_id`、`severity`、`rule_ref`、`evidence`、`repairability`、`recommended_fix` |

枚举值：`priority` 为 `MUST`、`SHOULD`、`MAY`、`CONDITIONAL`、`UNKNOWN`；`status` 至少为 `candidate`、`approved`、`deprecated`、`rejected`。任何 `UNKNOWN` 或低置信度观察不得生成 `approved` 规则。

## 9. 企业实例包与隔离

```text
enterprise-ppt-skill/
├── SKILL.md                         # 通用工作流，只引用受控接口
├── core/
│   ├── orchestration/
│   ├── schemas/
│   ├── validators/
│   └── references/
├── instances/
│   └── <company-id>/
│       ├── instance.yaml             # ID、兼容核心版本、策略与资产清单
│       ├── taxonomy/                 # 既有业务/部门/风格分类及映射
│       ├── brand/                    # 共享基线、许可与禁用项
│       ├── styles/<style-id>/        # Style Profile、Token、规则、例外
│       ├── templates/                # 受版本管理的 PPT/POTX 与版式索引
│       ├── evidence/                 # 清单和指针；原始样本可置于受控存储
│       ├── scenarios/                # 场景—风格—模板映射
│       ├── qa/                       # 审核阈值、规则与修复白名单
│       ├── versions/                 # 变更日志、迁移和审批记录
│       └── tests/                    # 脱敏/获授权的测试夹具与期望结果
└── tools/                            # 不含企业数据的通用解析与验证工具
```

隔离要求：

- 所有运行请求必须携带唯一 `company_id`，核心加载器拒绝路径穿越、缺失实例或跨实例引用。
- Schema 引用只能解析到当前实例或核心的只读资源；`source_id`、模板引用和证据引用必须带实例前缀。
- Agent 提示词只注入当前实例的必要片段、模板和证据摘要，不注入其他企业资产。
- 输出、缓存、日志和中间观察结果按 `company_id` 命名空间存放；跨实例检索默认关闭。
- 核心升级由 `instance.yaml` 的兼容版本锁定；迁移先在副本验证，通过后才提升实例声明的核心版本。

## 10. 两条工作闭环

### A. 风格学习与固化

`导入样本 → 解析/渲染 → 专业观察 → 三层聚合 → 交叉审核 → 人工审批 → 发布 StyleProfile`

新规则必须证明出现频率和适用范围。新分类先进入 `candidate`，只有人工审批后才成为正式分类或可被路由。

### B. 场景化生成与审核

`需求解析 → 场景/风格路由 → 选择模板与规则 → 生成 PPT → 结构/视觉 QA → 安全修复 → 复审 → 交付`

自动修复仅限已批准的机械性修复白名单，例如溢出、已知模板占位符、对齐和 Token 替换。改变业务结论、图表含义、正式分类或风格选择必须升级为人工确认。

### 10.1 本地审批界面与兼容入口

首版允许提供一个只连接当前电脑本地目录的轻量界面，用于浏览候选风格、证据、审核发现和发布差异，并执行批准/拒绝/退回操作。界面不是唯一入口：同一操作必须可由版本化审批文件或命令入口完成。

这保证不同模型、没有浏览器自动化能力的环境、或无界面部署均可兼容：它们只消费和写入经过 Schema 验证的 `ApprovalRequest`/`ApprovalDecision` 文件；本地界面只是这些契约的可视化客户端。首版不要求联网、账号体系或跨电脑协作。后续接入企业 SSO、审批系统或服务端时，新增适配器而不更改核心审批状态机。

## 11. 版本与变更治理

- 风格、模板、场景映射和 QA 规则独立版本化；一个风格升级不得影响其他风格。
- 每个发布记录新增、修改、弃用、原因、来源、影响范围、审批者和回滚目标。
- 对既有分类的删除、合并、拆分、重命名或层级调整属于破坏性变更，必须生成影响分析和前后映射，并等待确认。
- 发现无法归类的新样本时，只创建 `candidate` Profile，保留全部证据，不影响现有路由。

## 12. 验证策略与验收标准

首版在没有企业样本时只做静态验证，不能声称风格识别或 PPT 生成已通过真实样本测试。各实例上线前需提供获授权或脱敏的夹具，至少验证：

1. 已有分类、名称和映射未被意外修改。
2. 三维分类不会混淆，且支持混合风格标签。
3. 观察输出全部通过 Schema 验证，且每条已批准规则有证据。
4. PPTX 结构事实与渲染视觉结果正确记录来源类型和不确定性。
5. 路由器在匹配充分时选择预期风格，在不足时要求确认。
6. 模板生成后能通过文件结构、占位符、溢出、重叠、字体替换和风格规则 QA。
7. 不同 `company_id` 的加载、缓存、引用和日志不能交叉访问。
8. 核心升级、实例回滚和风格版本切换可复现。

### 12.1 公开样本闭环测试

框架测试可使用公开、获授权的 PPT/POTX 样本，但这些样本只能进入 `examples/` 或测试夹具，绝不作为任何企业实例的风格事实。优先从 Microsoft 的公开模板渠道获取，并在每个夹具清单中记录原始 URL、获取日期、许可/使用说明、文件哈希和用途。Microsoft 支持文档说明 Office 可获取免费预置模板并可用于自定义，[官方说明](https://support.microsoft.com/en-us/office/foundations-experiences/download-free-pre-built-templates)；其 PowerPoint 指南也明确将模板保存为 `.potx` 并通过母版与布局复用，[官方说明](https://support.microsoft.com/en-US/PowerPoint/create-and-save-a-powerpoint-template)。

测试闭环至少包含：导入公开样本、提取结构与视觉观察、生成候选规则、验证候选不会直接发布、从零生成一份新 PPTX、执行结构/视觉 QA、记录降级覆盖率；随后再用企业获授权样本验证企业实例化流程。

## 13. 实施边界与后续计划

本设计文档批准后，实施按以下顺序推进：

1. 建立空的通用核心目录、Schema 和实例包契约；不放入企业真实资产。
2. 为 Agent、路由、审核和隔离分别编写测试/夹具，并先验证失败场景。
3. 在测试驱动下编写 SKILL.md 与最小验证工具。
4. 创建一个不含企业数据的示例实例包，验证版本、加载和隔离流程。
5. 再由各企业内网团队基于示例实例化、导入模板和样本，并完成本企业审批。

已确认的首版前提：从零生成、模型可替换、能力探测与安全降级、每个实例存放在使用者电脑的本地目录、九个观察员均实现自动化任务契约、每实例支持 2–20 份样本，以及可选本地审批界面。
